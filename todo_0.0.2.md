# План выпуска pob2_engine 0.0.2

Следующий выпуск после [0.0.1](docs/RELEASE-0.0.1.md). Цель — расчёт попаданий
заклинаний трёх стихий и подбор поддержек через самостоятельный Go-движок.
CLI, MCP и gRPC используют общее ядро, сессии и неизменяемые сравнения.
Подключение Flutter остаётся отдельным этапом.

## 0. Границы выпуска

- [x] **0.1.** Выбрать Fireball / Frostbolt / Spark уровней 1–20, качества 0.
  Fireball и Frostbolt — режим Projectile, Spark — Base: одно попадание
  выбранного умения по одной цели. Число снарядов не умножает DPS автоматически.
- [x] **0.2.** Сохранить Rapid Casting I и Controlled Destruction; добавить
  предпросмотр их влияния в полной выбранной группе без изменения сессии.
- [x] **0.3.** Запланировать базовые характеристики восьми классов без возвышений.
  Пассивы других классов за пределами стартового узла пока не объявлять поддержанными.
- [x] **0.4.** Сохранить покрытие украшений и модификаторов `0.0.1`; расширить
  процентный урон и сопротивления противника для холода и молнии.
- [x] **0.5.** Оставить за рамками атаки, оружие/броню, полный граф дерева,
  возвышения, уникальные предметы, ailments, конверсию, дополнительный плоский
  урон, ауры, резервирование и UI. Взрывы Frostbolt/Fireball, повторные попадания
  Spark и взаимодействия Chill/Shock/Infusion не входят в показатели этого выпуска.

## 1. Основа и совместимость

- [ ] **1.1.** Зафиксировать исходное состояние: 77 вариантов `0.0.1`, прежние
  ключи Fireball, сохранённый результат и безопасный повтор после обновления.
- [ ] **1.2.** Сохранить закреплённые PoB/MCP и лицензии. Не совмещать расширение
  расчётов с обновлением upstream; новые исходные пути учитывать в манифестах.
- [x] **1.3.** Описать [таблицу покрытия](docs/COVERAGE-0.0.2.md), статусы и отсутствующие механики.
  Будущие возможности в таблице отличать от уже проверенных.

**Готовность:** исходный релиз остаётся воспроизводимой базой; сохранённые числа
не пересчитываются при открытии новой версией. Изменение набора получает новый ID.

## 2. Эталон и данные трёх стихий

- [ ] **2.1.** Получить отдельные XML/JSON Lua для Frostbolt и Spark: все уровни,
  две поддержки отдельно/вместе, модификаторы, сопротивления, границы и требования.
- [ ] **2.2.** Добавить воспроизводимый экспорт типа урона, режима и числовых
  значений камней. Отказаться от допущения «первые два поля всегда огонь»;
  искать точные исходные имена показателей и проверять состав.
- [ ] **2.3.** Ввести проверяемую схему набора 2 и новый ID. Проверять типы урона,
  режимы, диапазоны, идентификаторы и независимость возвращаемых значений.
- [ ] **2.4.** Закрепить отдельно новые эталоны и воспроизведение в Linux CI;
  старые 77 случаев сохранить без изменения ожидаемых чисел.

**Готовность:** данные экспортируются повторно без разницы; Lua и Go используют
одинаковые XML, режимы, версии и условия. Неподдержанное свойство не скрывается.

## 3. Общее ядро попаданий

- [ ] **3.1.** Убрать привязку результата и формул к Fireball. Выбирать параметры
  активного умения из проверенного набора; отклонять неизвестные режимы.
- [ ] **3.2.** Рассчитывать огонь, холод и молнию с правильными областями
  увеличений, множителей, критических попаданий и сопротивления противника.
- [ ] **3.3.** Сохранить прежние ключи/числа Fireball; для новых типов выдавать
  соответствующие промежуточные показатели, без выдуманных нулевых результатов.
- [ ] **3.4.** Сравнить все новые случаи с Lua, включая округление, предупреждения,
  неподдержанные условия, несовпадающие идентификаторы и выбранный режим.
- [ ] **3.5.** Проверить параллельное сравнение разных умений, отмену и отсутствие
  загрязнения состояния между сессиями.

## 4. Классы и выбор умения

- [ ] **4.1.** Проверить по Lua базовые характеристики и ресурсы восьми классов,
  требования трёх камней и стартовые узлы на нескольких уровнях персонажа.
- [ ] **4.2.** Разрешить подтверждённые базовые классы; возвышения и неизвестные
  пассивы по-прежнему отклонять. Недостаточные требования дают диагностику.
- [ ] **4.3.** Проверить смену главной группы между тремя умениями, неактивные
  группы/наборы и сохранение выбора после перезапуска.

## 5. Каталог и предпросмотр поддержек

- [ ] **5.1.** Добавить общий сервис каталога: точные ID, псевдонимы, уровни,
  режимы, семейства поддержек и границы расчётного покрытия. Данные каталога
  не должны обещать поддержку всех механик присутствующего класса/предмета.
- [ ] **5.2.** Предоставить ограниченный поиск/выборку через CLI, MCP и gRPC.
  Расширить Protobuf совместимо и обновить генерируемый Go/Dart API.
- [ ] **5.3.** Добавить предпросмотр поддержки через сравнение полного снимка
  группы: совместимость, повтор семейства, показатели до/после и причины отказа.
- [ ] **5.4.** Проверить одинаковые результаты трёх адаптеров, отсутствие новой
  ревизии/события при предпросмотре и отсутствие обхода ограниченной очереди.

## 6. Сессии и обновление

- [ ] **6.1.** Проверить открытие журнала `0.0.1`, прежние результаты `request_id`,
  привязку к старому набору и новый расчёт с актуальным набором без потери истории.
- [ ] **6.2.** Проверить импорт/правку/расчёт всех трёх умений отдельными процессами,
  события после commit, конфликты, отмену, backup/restore и аварийный перезапуск.
- [ ] **6.3.** Если изменение формата всё же понадобится, сначала подготовить
  миграцию с копией и отказом от сброса повреждённых данных. Без необходимости
  версию журнала не менять.

## 7. Приёмка и выпуск

- [ ] **7.1.** Обновить руководства, матрицу инструментов старого MCP и ограничений,
  примеры трёх умений и запись CHANGELOG. Проверить происхождение и лицензии.
- [ ] **7.2.** Пройти Linux CI: анализ, тесты, `-race`, старые/новые эталоны,
  экспорт данных, совместимость контракта и генерация API.
- [ ] **7.3.** Измерить три умения и предпросмотр, указать среду и границы замеров.
  Сравнение скорости с Lua не заявлять без отдельного измерения.
- [ ] **7.4.** Добавить три умения и обновление сессии в проверку релизного архива.
  По тегу кандидата собрать на Linux и запустить архивы на Windows x64,
  Linux x64 и macOS arm64, затем повторить на скачанных файлах.
- [ ] **7.5.** После закрытия обязательных пунктов подготовить `0.0.2`, отправить
  тег, дождаться всех проверок, сверить артефакты и записать итоговый отчёт.

## Порядок реализации

Начать с **1–3**: таблица покрытия, эталоны, данные и законченный расчёт трёх
умений. Затем **4–6**: классы, каталог, предпросмотр и совместимость сессий.
Наличие плана или каталога не подтверждает готовность числового расчёта.
После законченного этапа обновлять пункты, CHANGELOG, выполнять проверки,
коммитить изменения и дожидаться CI. Обычные тесты — только Linux в CI;
платформенные сборки и запуски — по релизным тегам. Тег `v0.0.2` до приёмки
не создавать. Завершённый план `0.0.1` не переписывать.
