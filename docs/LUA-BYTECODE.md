# Байткод LuaJIT

## Штатная сборка

Выпуск встраивает байткод мостов расчётчика и мастерской вместе с их
исходниками. Движок выбирает байткод, если SHA-256 фактической библиотеки
LuaJIT совпадает с библиотекой сборки. При другой библиотеке или ошибке
загрузки входа и отдельных модулей используются исходные файлы моста.
Локальная и обновлённая установки PoB совместимы с этим выбором.

Генератор работает на целевой платформе. Windows использует `lua51.dll`
закреплённой установки PoB. Linux x64 и macOS arm64 используют нативную
библиотеку из того же архива, который встраивается в движок. Для одинаковых
входных файлов и библиотеки `string.dump` в режиме `d` записывает одинаковый
байткод. [Режимы LuaJIT](https://luajit.org/extensions.html#string_dump)

Из корня проекта выполните следующие команды нативно. На Linux и macOS
перед ними запустите [сборку нативной библиотеки](../tool/build_native_runtime.py).

```shell
go run ./cmd/pob2-engine pob-data ensure > pob-installation.json
python -X utf8 tool/compile_pob_bytecode.py --installation pob-installation.json
go build -tags=pob_bytecode ./cmd/pob2-engine
```

Штатный инструмент установки загружает оригинальные код и данные PoB из
официального выпуска. Встраиваются только мосты репозитория. Для проверки
можно включить `POB2_ENGINE_TRACE_LUA=1`. Рабочий процесс выводит в stderr
`pob2-lua: bytecode` или `pob2-lua: source` при загрузке моста. Режим
`POB2_ENGINE_LUA_SOURCE=1` принудительно включает исходные мосты для замеров.

## Эксперимент с полной копией PoB

В этом историческом замере отдельная копия установки содержит байткод
скриптов и игровых таблиц PoB под прежними именами `.lua`. Сборка с тегом
`pob_bytecode` дополнительно включает байткод мостов. Контроль использует
текстовые Lua-файлы. В обоих вариантах используется одна библиотека LuaJIT.
Замер оценивает полную конвертацию, включая файлы вне комплекта движка.

## Подготовка

Из корня `pob2_engine` на Windows укажите установленный PoB v0.23.1 и
новый каталог для прогона. Генератор использует стандартную библиотеку Python
и `lua51.dll` из этой установки. Исходный каталог PoB открывается для чтения.

```powershell
$pob = 'C:/path/to/installed/PoB'
$experiment = '.reference/bytecode-tree'
New-Item -ItemType Directory -Path $experiment
python tool/compile_pob_bytecode.py --pob $pob --library "$pob/lua51.dll" `
  --source-copy "$experiment/pob-source" --output "$experiment/pob-bytecode"
go build -o "$experiment/engine-source.exe" ./cmd/pob2-engine
go build -tags=pob_bytecode -o "$experiment/engine-bytecode.exe" ./cmd/pob2-engine
```

Генератор записывает мост в игнорируемый каталог `internal/pob/bytecode`.
В обеих копиях PoB чтение `TreeData/.../tree.lua` переведено в двоичный
режим. Это сохраняет содержимое при чтении байткода на Windows.

## Замер через gRPC

```powershell
$fixture = '../pob2_ui/integration_test/fixtures/witch_fireball.xml'
go run ./tool/measure_tree_latency --baseline "$experiment/engine-source.exe" `
  --candidate "$experiment/engine-bytecode.exe" `
  --baseline-pob "$experiment/pob-source" --candidate-pob "$experiment/pob-bytecode" `
  --fixture $fixture --node 51184 --cold 3 --warm 20 > "$experiment/tree-rpc.json"
```

В каждом раунде запускаются новые процессы сервера и мастерской.
Первый выбор пассива измеряется после открытия дерева. Остальные выборы
используют те же процессы с новым снимком из того же XML. Порядок вариантов
меняется между раундами. Первый отчёт Lua и готовность дерева записываются
отдельно от задержек выбора и подтверждения. Холодный замер означает, что
процессы Lua начали работу в этом раунде. Файловый кэш Windows сохраняется.

Сценарий проверяет, что предпросмотр сохраняет исходный снимок, применение
добавляет ожидаемый узел и создаёт одну ревизию, а актуальный отчёт возвращает
те же показатели, что и предпросмотр. Для сравнения между вариантами сверяются
путь узлов, хеши снимков и проверенные характеристики. В JSON сохраняются
все измерения и p50/p95 в наносекундах.

пришлось три первых и двадцать прогретых измерений. В таблице p50.

| Этап | Исходный Lua | Байткод |

| Открытие сборки до полной сцены, новые процессы | 5,79 с | 4,56 с |
| Первый предпросмотр после открытия дерева | 976 мс | 660 мс |
| Повторный предпросмотр после прогрева | 1002 мс | 742 мс |

| Подтверждение до полной сцены после прогрева | 2548 мс | 2038 мс |

Измеряли назначение Raw Destruction (51184). Оба варианта добавили один и

## Замер в окне PoB II

В Windows Flutter Debug выполнены четыре запуска в порядке A–B–B–A.
В каждом запуске тест кликает Raw Destruction на холсте, подтверждает
назначение, затем кликает тот же узел и подтверждает снятие. В тесте
проверяются появление числа в диалоге, новая ревизия, состав дерева и
изменение главного DPS в боковой панели. У каждого действия по два
наблюдения на вариант. В таблице медианы.

| Действие в окне | Исходный Lua | Байткод |
| --- | ---: | ---: |
| Клик по неназначенному узлу → число предпросмотра | 0,99 с | 0,95 с |
| Подтверждение назначения → новый FullDPS в панели | 3,37 с | 3,68 с |
| Клик по назначенному узлу → число предпросмотра снятия | 1,34 с | 0,97 с |
| Подтверждение снятия → новый FullDPS в панели | 2,94 с | 3,77 с |

FullDPS после назначения равен 33,314095 в обоих вариантах, после снятия —
30,054529. Снятие убирает выбранный узел и сохраняет промежуточные пассивы.
В этой серии ускорение вызовов движка сопровождалось более ранним
предпросмотром. Время до обновления боковой панели оказалось выше
на байткоде. Для оценки этой разницы нужна более длинная серия с раздельными
замерами отчёта, сцены, записи XML и отрисовки.

Для повторения укажите абсолютные пути в `POB2_ENGINE_TEST_EXECUTABLE`,
`POB2_ENGINE_POB_DIR` и `POB2_TREE_PERF_OUTPUT` для каждой пары бинарника,
установки и нового файла JSONL. Задайте `POB2_TREE_PERF_SAMPLES=2` и метку
прогона в `POB2_TREE_PERF_VARIANT`. Команда выполняется из `pob2_ui`.

```powershell
flutter --no-version-check test integration_test/tree_bytecode_perf_test.dart -d windows --no-pub --reporter expanded
```

## Путь до нового DPS в Windows Release

Windows Release собран с обычной точкой входа PoB II. В каждом из
четырёх запусков A–B–B–A выполнены назначение, снятие, повторное
назначение и повторное снятие узла 51184. Каждый запуск начинался с
одного и того же XML `witch_fireball.xml` в новом профиле. Все 16
применений подтвердились в XML и визуальном показателе. При назначении
FullDPS изменился с 22,419132 до 33,314095 в обоих вариантах.

Начало интервала — обработчик кнопки «Применить». Конец — завершение
растеризации первого кадра Flutter с новым числом. Кадр сопоставляется
по `frameNumber` в момент отрисовки текста и в `FrameTiming`.
Значения в таблице — медианы двух наблюдений на действие и вариант.
Медиана общего интервала вычислена по полным трассам.

| Этап, мс | Первое назначение, Lua | Первое назначение, байткод | Повторное назначение, Lua | Повторное назначение, байткод |
| --- | ---: | ---: | ---: | ---: |
| Apply RPC | 374 | 266 | 352 | 239 |
| Экспорт прежнего XML для отката | 2091 | 941 | 10 | 6 |
| Загрузка нового XML в мастерскую | 383 | 388 | 328 | 300 |
| Отчёт Lua | 286 | 223 | 318 | 230 |
| Получение и подготовка геометрии дерева | 1688 | 1516 | 1691 | 1351 |
| Сохранение нового XML через библиотеку | 30 | 27 | 39 | 36 |
| Публикация состояния → первый кадр с DPS | 81 | 89 | 86 | 94 |
| **«Применить» → первый кадр с DPS** | **5029** | **3496** | **2865** | **2270** |

Геометрия занимает около 60% интервала повторного назначения и
запрашивается до публикации отчёта. Растеризация кадра занимала
около 5 мс при первом назначении и 14 мс при повторном. Фоновое
оформление дерева может продолжаться после кадра с новым DPS.

В одном контрольном прогоне с исходным Lua приложение ждало семь секунд
после открытия дерева и только затем впервые применяло узел. Экспорт
прежнего XML занял 5 мс, получение геометрии — 1416 мс, сохранение XML —
40 мс, весь интервал до первого кадра — 2440 мс. Экспорт и запросы текстур
проходят через общую очередь Workbench. Контроль показывает зависимость
длительности экспорта от момента применения. Для проверки роли очереди
нужен отдельный замер ожидания внутри Workbench.

Чтобы повторить замер, соберите PoB II командой
`flutter --no-version-check build windows --release --no-pub` и передайте
`POB2_UI_TREE_APPLY_TRACE` с путём к новому файлу JSONL при запуске
изолированного профиля. Сценарий в папке эксперимента
`.reference/bytecode-tree-20261125/measure-tree-release.py` запускает
выбранный Release с локальным MCP окна, проверяет DPS и содержимое XML.
В той же папке сохраняются `tree-release-v4-*.jsonl`,
`tree-release-settled-source.jsonl` и `tree-release-summary.json`.

### Публикация DPS до обновления геометрии

Повторный замер сравнивает прежний Windows Release со сборкой, в которой
отчёт публикуется после записи XML, а полная геометрия читается в фоне.
Оба варианта использовали один `engine-source.exe`, исходный Lua PoB и
один `witch_fireball.xml`. В четырёх изолированных запусках в порядке
«до, после, после, до» по очереди назначали и снимали узел 51184.
Все 16 правок подтверждены в XML и на панели. Первое назначение меняет
FullDPS с 22,419132 до 33,314095.

| Медиана, мс | Первое назначение, до → после | Повторное назначение, до → после | Снятие, до → после |
| --- | ---: | ---: | ---: |
| «Применить» → первый кадр с DPS | 4569 → 2759 | 2490 → 909 | 2850 → 999 |
| Запись XML | 36 → 20 | 38 → 23 | 34 → 24 |
| Конец записи XML → первый кадр с DPS | 75 → 71 | 98 → 62 | 89 → 68 |
| Получение и подготовка геометрии | 1429 → 1304 | 1424 → 1253 | 1490 → 1209 |
| Кадр с DPS → готовность геометрии | −111 → 1305 | −136 → 1254 | −121 → 1209 |

На каждый вариант пришлось по два первых назначения, по два повторных
назначения и по четыре снятия. Отрицательное время означает, что
геометрия была готова до кадра с DPS. Растеризация кадра в новой сборке
занимала примерно 6–7 мс. Полная загрузка текстур учитывается отдельно.
На первом назначении экспорт прежнего XML для отката занял 1,83 с по медиане.
Новая сборка также восстанавливает матовое стекло на экране дерева.
Сводка и имена сырых трасс сохранены в `tree-apply-ab-summary.json` в папке
эксперимента.
