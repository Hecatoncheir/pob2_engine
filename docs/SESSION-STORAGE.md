# Сохранение и восстановление сессий

Сервер профиля сохраняет каждую принятую команду до успешного ответа CLI или MCP. После перезапуска восстанавливаются текущие снимки, ревизии и результаты прежних команд. Автоматическое завершение больше не удаляет сборки.

## Запуск и расположение данных

```powershell
.\pob2-engine.exe connect --profile main --start-server
.\pob2-engine.exe info --profile main
```

`info` сообщает `storage_mode: disk`, путь `storage_path` и возможность `session.persistence`. Режим жизни `automatic` или `persistent` не меняет сохранение. Обычный `serve` без имени использует профиль `default` и также сохраняет сессии.

По умолчанию база расположена в `<os.UserConfigDir()>/pob2-engine/profiles/<профиль>/sessions.db`. Для другого базового каталога задайте `--data-dir DIR`. Его нужно повторять при последующих запусках; смена флага сама не переносит существующие данные. Если сервер уже запущен с другим каталогом, подключение с явно несовпадающим `--data-dir` возвращает ошибку.

`--runtime-dir` управляет только служебным каталогом обнаружения. Удаление или смена этого каталога после остановки не затрагивает базу. При одинаковом профиле и `--data-dir` сервер восстанавливает сессии даже с новым каталогом обнаружения.

Для намеренно временной работы доступны `serve --ephemeral` без профиля и каталогов данных, а также `mcp --standalone`. Они используют память и не объявляют `session.persistence`. Подключение по профилю к старому серверу без сохранения отклоняется; `info` и `shutdown` остаются доступны для его проверки и остановки. Подключение по явным адресу и токену сохраняет возможность работы с временным сервером.

## Что сохраняется

- Создание сессии, её идентификатор, название сборки и исходная ревизия.
- Каждое успешное переименование, ожидаемая и полученная ревизии.
- `request_id`, аргументы команды и её первоначальный результат.
- Полный XML, SHA-256 входа, последняя ревизия входных данных и JSON результата
  расчёта с привязкой к набору данных через общий сервис CLI/MCP/gRPC.

Точный повтор после перезапуска возвращает тот же результат, включая старую ревизию, и не меняет текущий снимок. Повтор идентификатора с другими аргументами отклоняется. Для создания идентификаторы уникальны в пределах сохранённого профиля, для остальных правок — в пределах сессии. Лимиты 1024 сессии и 4096 команд на сессию не сбрасываются перезапуском.

Аренды, токены подключения, идентификатор экземпляра и активные задачи не записываются в журнал сборок. Новый сервер имеет новый `instance_id`; клиенты регистрируются заново. Восстановление сохранённого расчёта не запускает формулы заново. Подробности — в [BUILD-COMMANDS.md](BUILD-COMMANDS.md).

## Порядок подтверждения

1. Общий сервис проверяет аргументы, повтор команды и ожидаемую ревизию под блокировкой сессии.
2. Команда и её результат добавляются в транзакционный журнал.
3. После успешного commit обновляются снимок в памяти и таблица результатов.
4. Клиент получает успешный ответ.

Повтор успешной команды не создаёт вторую запись. Отмена до commit откатывает транзакцию. Если соединение оборвалось после commit, повтор прежнего `request_id` позволяет получить уже сохранённый результат.

Ошибка записи возвращается как `storage_failure` / gRPC `Unavailable`; неподтверждённое изменение не публикуется в памяти. После ошибки самой базы дальнейшая запись блокируется до перезапуска: результат сбоя во время commit может быть неопределённым. Восстановление читает фактически сохранённый журнал; повтор того же идентификатора разрешает неопределённость без двойного применения.

[WatchSession](SESSION-EVENTS.md) отправляет события общего сервиса после commit и обновления состояния. Повторы не порождают новых событий. Подключение Flutter отложено.

## Формат, защита и ошибки запуска

Используется [bbolt](https://github.com/etcd-io/bbolt) `v1.5.0`, транзакционное встраиваемое хранилище на Go. Версия закреплена в `go.mod`, исходная лицензия MIT сохранена в [.licenses/bbolt.LICENSE](../.licenses/bbolt.LICENSE). Отключение синхронизации с диском не используется.

Формат приложения имеет версию `2`: metadata, счётчик полезных байтов и упорядоченные записи команд. Каждая запись содержит JSON и контрольную сумму SHA-256. Перед публикацией готовности проверяются структура базы, версия, последовательность записей, суммы, размер и восстановление состояния. Ранее сохранённые числа не пересчитываются.

При повреждении, неизвестной версии или занятой базе сервер сообщает ошибку и не переходит к работе в памяти. Исходный файл не сбрасывается автоматически. Одну базу одновременно открывает только один процесс, даже если два сервера используют разные каталоги обнаружения. Права каталога ограничены текущим пользователем: `0700`/`0600` на Unix, DACL на Windows.

При остановке сначала завершаются RPC и задачи, затем закрывается база и только после этого удаляется файл подключения и освобождается блокировка профиля. Дополнительная финальная запись не нужна: каждая подтверждённая команда уже зафиксирована.

При открытии версии `1` сначала полностью проверяется её восстановление,
затем рядом создаётся `sessions.db.v1-<случайный ID>.bak` и только после
успешного Sync меняется схема. Неизвестная или повреждённая старая база
не мигрируется. Исходные записи остаются без изменения.

Пакет `storage` предоставляет `Backup`, `Verify`, `Restore`. Копия создаётся
через согласованную read-транзакцию bbolt и подтверждается после Sync;
существующий файл не перезаписывается. Проверка открывает файл только для чтения,
проверяет страницы, контрольные суммы, порядок и полное восстановление.
Восстановление допускается только в новый профиль без существующей базы.
Команды CLI `storage backup|verify|restore` описаны в
[CLI-BUILDS.md](CLI-BUILDS.md). Для доступа к занятой базе отдельным процессом
сначала требуется остановить сервер.

Журнал ограничен 128 МиБ полезных записей, одна запись — 8 МиБ. Физический
файл bbolt может занимать больше из-за страниц и резерва. Переполнение
возвращает `resource_exhausted`, не блокирует журнал как неисправный диск
и не удаляет историю. Экспорт и чтение остаются доступны.

## Проверки

Модульные и процессные тесты входят в `go test ./...`; CI выполняет их и `go test -race ./...` только на Linux. Проверяются:

- Автоматическое завершение и восстановление правок CLI/MCP с прежними ревизиями и результатами повторов.
- Принудительный `Kill` после успешного ответа и запуск с новым каталогом обнаружения.
- Отказ записи, сохранение прежнего снимка и последующая корректная обработка идентификатора команды.
- Параллельные записи разных сессий и эксклюзивное открытие общей базы.
- Повреждённые данные, неизвестная схема, неверный каталог и отсутствие автоматического сброса.

Это проверки перезапуска процессов и обработки ошибок; испытание физического отказа носителя не проводилось.

[Приёмка сессий 0.0.2](SESSION-ACCEPTANCE-0.0.2.md) распространяет полную
цепочку на Fireball/Frostbolt/Spark: 18 отмен через CLI/MCP/gRPC, 6 остановок
перед/после commit, потеря ответа, восстановление трёх сессий и общей копии.
Числа, первоначальные ответы и история проверяются после запуска нового сервера.
