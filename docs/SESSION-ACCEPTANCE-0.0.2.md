# Проверка сессий и восстановления 0.0.2

Пункт 6.2 [плана выпуска](../todo_0.0.2.md). Проверки входят в `go test ./...`
и Linux CI с `-race`. Flutter не участвует. Приёмка релизных архивов остаётся
этапом 7.

## Сценарии

| Проверка | Подтверждение |
| --- | --- |
| Три независимые сессии | Fireball, Frostbolt, Spark: CLI импортирует XML, MCP добавляет +100% Spell Damage, gRPC рассчитывает; три адаптера читают одинаковый снимок |
| События | У импорта, правки, расчёта и переименования проверяются ревизия, request_id, вид, изменённое поле, XML, хеши, числа и происхождение результата |
| Конфликты | Старая ревизия отклоняется через каждый адаптер; занятый request_id — через gRPC. Текущий снимок остаётся прежним |
| Аварийный перезапуск | После подтверждённых команд процесс принудительно завершается; новый сервер с новым runtime-каталогом восстанавливает три сессии, числа и историю |
| Повтор после перезапуска | Импорт через gRPC, правка через MCP и расчёт через CLI возвращают первоначальные ответы ревизий 2/3/4; текущая ревизия 5 не откатывается |
| Резервная копия | Остановленный профиль проходит CLI backup/verify/restore в новый профиль; восстанавливаются все три сессии, ответы и история |
| Отмена | 18 случаев: три умения × CLI/MCP/gRPC × до/после записи. Отмена до commit сохраняет прежний снимок; после commit результат остаётся принятым |
| Потеря ответа при Kill | Шесть случаев: три умения × остановка перед записью/после успешного commit, до публикации результата и ответа клиенту |

После +100% Spell Damage ожидаемый `TotalDPS` равен `17.8333333333333`, `18.2`,
`17.1285714285714` соответственно; абсолютный допуск — `1e-9`.
Переименование сохраняет XML и расчёт. Восстановленные числа и JSON сравниваются
с первоначальным снимком, без нового запуска формул для успешного `request_id`.

Общая копия содержит ровно 15 записей: пять подтверждённых команд на сессию.
Каждый сценарий отмены/потери ответа заканчивается ровно тремя записями:
создание, импорт, один принятый расчёт. Повторы и отклонённые команды записей
не добавляют. События воспроизводятся после перезапуска; лишние события
от повторов/конфликтов проверяются отдельно.

## Управляемая остановка

[Тестовый сервер](../internal/integration/recovery_gate_test.go) запускается
отдельным процессом и использует настоящий сервис и bbolt с включённым Sync.
Обёртка журнала приостанавливает расчёт до `Append` либо после его успешного
возврата. Родитель ждёт сигнал барьера и только затем отменяет запрос или
завершает процесс. Отмена после commit не меняет успешный результат записи.
Рабочий сервер не получает тестовых флагов или задержек.

После Kill запускается обычный собранный CLI-сервер. До commit он видит прежнюю
ревизию; после commit — сохранённый результат, даже если клиент не получил ответ.
Повтор с теми же `request_id` и входом разрешает неопределённость без повторной
записи. Проверяются один итоговый расчёт и одно событие.

Барьер ставится после вычисления формул, на границе сохранения. Проверки
охватывают отмену RPC, разрыв CLI-процесса и перезапуск сервера; физический отказ
носителя и прерывание внутри системного вызова записи не моделируются.

## Формат и запуск

Формат журнала остаётся **2**. Новая миграция для `0.0.2` не требуется;
[проверка базы выпущенного 0.0.1](../internal/storage/release_compat_test.go)
и прежние проверки повреждений/миграции сохраняются. Повреждённая база
не сбрасывается автоматически.

```shell
go test ./internal/integration -run '^TestThreeSpell' -count=1
go test ./...
go test -race ./...
```

Последняя команда выполняется в Linux CI. Основные сценарии:
[сессии и копии](../internal/integration/session_recovery_test.go),
[отмена и границы commit](../internal/integration/recovery_boundary_test.go).
[Отчёт сложности](../testdata/quality/0.0.2-stage6.json) охватывает новые и
изменённые функции, включая тесты; максимум COG — 8.
