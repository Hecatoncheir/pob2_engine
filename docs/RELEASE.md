# Установка, обновление и проверка выпуска

Со [страницы выпусков](https://github.com/Hecatoncheir/pob2_engine/releases)
скачайте файл для своей платформы и `SHA256SUMS`.

| Платформа | Файл |
| --- | --- |
| Windows x64 | `pob2_engine_TAG_windows_amd64.exe` |
| Linux x64 | `pob2_engine_TAG_linux_amd64` |
| macOS arm64 | `pob2_engine_TAG_darwin_arm64` |

Сравните SHA-256 файла с указанным в `SHA256SUMS`. В Windows используйте
`Get-FileHash ИМЯ_ФАЙЛА -Algorithm SHA256`, в Linux — `sha256sum -c SHA256SUMS --ignore-missing`,
в macOS — `shasum -a 256 ИМЯ_ФАЙЛА`. Затем переименуйте файл в
`pob2-engine.exe` или `pob2-engine`. На Linux/macOS выполните `chmod +x pob2-engine`.
При первом запуске с пустым кэшем движок загружает закреплённый PoB v0.23.1,
сверяет размер и SHA-256, устанавливает нативные библиотеки и проверяет
запуск LuaJIT. Для Linux и macOS LuaJIT и lua-utf8 встраиваются при сборке
движка из закреплённых исходников. Для Windows библиотеки входят в официальный
архив PoB. Этот сценарий используют сервер, автономный MCP и локальный
расчёт. Установленный PoB работает офлайн. Для перехода на новый стабильный
PoB используйте `update --target pob`. Команда `pob2-engine doctor --licenses`
выводит уведомления, включённые в бинарник.

## Самообновление

```shell
pob2-engine update --check
pob2-engine update
pob2-engine update --target pob
pob2-engine update --check --target engine
pob2-engine doctor
pob2-engine doctor --profile default
```

По умолчанию команды обслуживают запущенный бинарник CLI. Для обслуживания
существующего сервера укажите `--profile` или `--address` и `--token`.
Подключённый MCP обслуживает сервер, автономный MCP — свой процесс.

| Операция | CLI | MCP | gRPC `SessionService` |
| --- | --- | --- | --- |
| Проверить выпуск | `update --check` | `update {}` | `Update { apply: false }` |
| Установить выпуск | `update` | `update {"apply":true}` | `Update { apply: true }` |
| Проверить состояние | `doctor` | `doctor {}` | `Doctor {}` |

Выберите `all`, `engine` или `pob` через `--target` в CLI и поле `target` в
MCP/gRPC. По умолчанию проверяются оба компонента. Для перехода на конкретный
стабильный выпуск PoB укажите `pob@vX.Y.Z`. Статус `partial` означает,
что один из компонентов не удалось проверить или обновить. Подробность указана
в его поле `message`.

Для проверок с ограниченной квотой GitHub можно задать токен чтения в
`POB2_ENGINE_POB_GITHUB_TOKEN`. Движок использует его только для метаданных
официального репозитория PoB на `api.github.com`. Релизные задания задают
эту переменную через токен GitHub Actions.

Обновление берётся из стабильного выпуска GitHub. Установщик сравнивает версии,
выбирает бинарник для текущей ОС и архитектуры, сверяет размер и SHA-256
с опубликованными метаданными и `SHA256SUMS`. Сборка `dev` показывает
доступную версию. Самоустановка доступна для сборок с релизным тегом и при
наличии права записи в каталог установки.

### Переход с v0.0.8

Перед обновлением остановите сервер и сохраните копию базы командой
`storage backup --profile default --file backup.db`. Движок `v0.0.9`
открывает базы `v0.0.8`. Из сохранённой сессии доступны XML, расчёт и исходные
ответы `request_id`, в том числе после первой примерки предмета.

### Переход с v0.0.7

Перед обновлением остановите сервер и сохраните копию базы командой
`storage backup --profile default --file backup.db`. Движок `v0.0.8`
восстанавливает XML, сохранённые расчёты и исходные ответы `request_id`
из базы `v0.0.7`. Для возврата на прежнюю версию восстановите в отдельный
профиль копию, созданную до обновления.

### Переход с v0.0.6

Перед обновлением остановите сервер и сохраните копию базы командой
`storage backup --profile default --file backup.db`. Выпуск `v0.0.7`
открывает базы `v0.0.6` и восстанавливает исходные ответы `request_id`.
Для возврата на `v0.0.6` восстановите резервную копию, сделанную до
обновления, в отдельный профиль. Это позволяет сохранить обе базы.

### Переход с v0.0.2

Для первого перехода скачайте бинарник v0.0.3 и проверьте его по
`SHA256SUMS`. Завершите сервер v0.0.2 и сохраните копию базы командой
`storage backup --profile default --file backup.db`. Укажите имя своего
профиля и прежний `--data-dir`, если задавали его при запуске.
Сохраните прежний бинарник рядом, замените его на скачанный и запустите
тот же профиль. Команда `doctor --profile default` покажет версию движка,
установленный PoB и путь к базе. Последующие выпуски можно ставить через
`update`.

### Перезапуск и восстановление

`updated` с `restart_required: true` означает, что установлен новый бинарник
или версия Lua. Сервер берёт новую версию при следующем запуске.
Работающий сервер или MCP завершите штатно и запустите снова. В Windows
запущенный образ может временно остаться в соседнем каталоге
`.pob2-engine-previous-*`. После выхода старого процесса этот каталог можно удалить.
Если во время замены произошёл аварийный выход и исходный файл отсутствует,
верните прежний бинарник из этого каталога на его исходный путь.
Сессии открываются штатным запуском новой версии.

Перед активацией установщик проверяет каталог и рассчитывает три
многогрупповые сборки. При сбое действующая версия PoB остаётся активной.
Проверить возможность отката и выбрать предыдущую установку можно командами

```shell
pob2-engine update --check --target pob-rollback
pob2-engine update --target pob-rollback
```

Откат использует локальный кэш и работает без сети и без запущенного
сервера. При `rollback_available` доступна предыдущая установка. После
`rolled_back` запустите сервер заново с прежним профилем. Откат в MCP и gRPC
использует ту же цель `pob-rollback`. Для записи передайте `apply: true`.
Откат хранит одну предыдущую версию, записанную при успешном обновлении PoB
движком `0.0.6`. Установка с прежним манифестом входит в этот цикл с первого
управляемого обновления PoB.

Для запуска с вручную выбранной копией PoB задайте `POB2_ENGINE_POB_DIR`
с путём к каталогу `vX.Y.Z-SHA` в кэше `pob2-engine/pob`. На Linux и macOS
также укажите подкаталог `native` через
`POB2_ENGINE_POB_NATIVE_DIR`. Запускайте сервер с прежним профилем.
Чтобы вернуться к управляемой версии PoB, запустите его без этих переменных.

`doctor` проверяет исполняемый файл и целостность встроенного каталога. Поля
`engine_update` и `pob` показывают установленные версии, последние стабильные
выпуски и результат сетевой проверки. В состоянии `pob` поля `running_version`
и `running_commit` описывают установку, которую использует работающий процесс.
Поля `installed_version` и `installed_commit` описывают следующий запуск,
а `previous_version` и `previous_commit` — сохранённую установку для отката.
Поля версий и необходимость перезапуска доступны и без сети.
В JSON доступны версия, протокол, ОС и архитектура, Go, commit сборки,
ID и SHA-256 данных, версия дерева и ревизия PoB. Для сервера также доступны
его фаза, режим, аренды, активные задачи и состояние файла базы.
`degraded` сопровождается подробностями в `issues`.

## Условия публикации

Для стабильного выпуска без локального процесса запустите в GitHub Actions
«Выпустить движок» из ветки `main`. Укажите опубликованный `vX.Y.Z-rc.N`
и номер полной приёмки PoB II. Запустите эту приёмку с выбранным `engine_release`
и включёнными `locked_components` и `engine_workshop`.

В `main` заранее добавьте запись стабильной версии в `CHANGELOG.md`.
Workflow сверит исходники с кандидатом, закреплённый бинарник и Dart API
в PoB II и дождётся результата на всех трёх ОС. Затем GitHub соберёт
и проверит стабильные бинарники, создаст тег и опубликует выпуск.
Параметр `verify_only` ограничивает запуск проверкой условий.

Приёмка 0.0.4 дополнительно проверяет полный каталог оригинального PoB,
Ice Nova и Concentrated Area с качеством 20, несовместимую поддержку,
правки брони и нового пассива, точные повторы после перезапуска и переход
[базы v0.0.3](../testdata/compat/0.0.3/README.md). Числа нового умения
сверяются с [независимыми эталонами](../testdata/reference/0.0.4/README.md).

Тег `v*` должен указывать на коммит из `main` с непустой записью версии
в [CHANGELOG](../CHANGELOG.md). Тег с суффиксом создаёт предварительный выпуск.
Релизный workflow повторяет Linux CI, собирает три бинарника на целевых ОС
и проверяет каждый перед публикацией. Сборки Linux и macOS используют cgo
для подключения нативного LuaJIT.

Перед сборкой workflow подготавливает закреплённый PoB и компилирует мосты
той же библиотекой LuaJIT, которую затем проверяет в релизном сценарии.
Байткод встраивается в бинарник вместе с исходниками мостов. При смене
библиотеки движок загружает исходники. [Подготовка и замеры](LUA-BYTECODE.md).

Раннеры запускают `doctor` и полный сценарий расчёта Fireball, Frostbolt и
Spark без среды разработки, включая CLI/MCP/gRPC и восстановление сессий.
Сценарий Lua проверяет первую установку PoB, расчёт всех трёх сборок и
восстановление [базы v0.0.2](../testdata/compat/0.0.2/README.md).
После пересчёта и перезапуска старый и новый `request_id` возвращают свои
исходные ответы.

В отчётах фиксируется время готовности сервера, первый запрос каждого
умения и пять повторных запросов для Go и LuaJIT. Первый запрос Fireball
включает запуск процесса LuaJIT. Задержка запроса включает CLI, gRPC и
запись новой ревизии сессии. Замеры начинаются после установки PoB.

Отдельные тесты проверяют замену запущенного файла и отказ при повреждённом
обновлении. CI формирует и сверяет `SHA256SUMS` перед публикацией.
JSON-отчёты доступны в артефактах GitHub Actions.

Для ручного повторения на целевой платформе подготовьте исходники того же
тега и выполните:

```shell
python -X utf8 tool/smoke_release.py --binary ИМЯ_ФАЙЛА --checksums SHA256SUMS --tag TAG --report report.json
```

Для бинарников начиная с `v0.0.19-rc.1` добавьте `--require-bytecode`.
Проверка подтверждает загрузку байткода при повторном расчёте без сети.

В `v0.0.2` и более ранних выпусках использовались ZIP-архивы. Их состав
и порядок проверки описаны в документации соответствующих тегов.
