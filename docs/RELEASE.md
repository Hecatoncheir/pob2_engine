# Проверка и установка выпуска

## Состав

Выпуски по тегам `v*` содержат ZIP для Windows x64, Linux x64 и macOS arm64.
Внутри — `pob2-engine[.exe]`, документация, три минимальных XML, эталон обновления
сессии опубликованного `0.0.1`, оригинальные лицензии,
происхождение формул и встроенных данных, `COMMIT.txt` и `PACKAGE.json` с
SHA-256 каждого файла. Для расчёта достаточно исполняемого файла: данные встроены.
Архивы исходников и отдельный комплект лицензий публикуются рядом.

Скачайте подходящий ZIP и `SHA256SUMS` со страницы версии. Сравните сумму
архива с указанной: `Get-FileHash ARCHIVE.zip -Algorithm SHA256` в PowerShell
либо `sha256sum ARCHIVE.zip` в Linux. На macOS: `shasum -a 256 ARCHIVE.zip`.
Распакуйте архив в отдельный каталог. На Linux/macOS при необходимости
разрешите запуск через `chmod +x pob2-engine`.

```shell
./pob2-engine --version
./pob2-engine calculate --file testdata/reference/fireball.xml
./pob2-engine calculate --file testdata/reference/0.0.2/cases/frostbolt-minimal.xml
./pob2-engine calculate --file testdata/reference/0.0.2/cases/spark-minimal.xml
```

В Windows используйте `./pob2-engine.exe`. Примеры возвращают `complete` и
`TotalDPS = 8.9166666666667 / 9.1 / 8.5642857142857` с установленным допуском.
Команды сессий, MCP, статусы и резервные копии: [CLI-BUILDS.md](CLI-BUILDS.md).
Проверяйте `status` и `issues`; границы кандидата — в [покрытии 0.0.2](COVERAGE-0.0.2.md).
Для исторического `0.0.1` действует [его покрытие Fireball](COVERAGE-0.0.1.md)
и сценарий проверки из исходников соответствующего тега.

## Условия публикации

Обычный CI выполняет все тесты только на Linux, включая `-race`, генерацию
контракта и сравнение с закреплённым Lua. Отчёт `calculation-performance-linux`
содержит замеры, Go, CPU и входы; [45 точек 0.0.2](PERFORMANCE-0.0.2.md)
закреплены отдельно и не являются сравнением скорости с Lua.

Только релизный тег запускает кросссборки на Linux с `CGO_ENABLED=0`.
Затем Windows, Linux и macOS запускают каждый свой готовый архив.
Проверяются SHA-256 состава, версия, три расчёта с пустым PATH, общие сессии
CLI/MCP через gRPC, девять инструментов MCP, каталог, шесть предпросмотров,
сравнение без правки, экспорт, резервная копия и точные повторы трёх сессий.
База настоящего опубликованного `0.0.1` открывается из копии: прежний результат
не меняется, новый использует актуальный набор, повтор старого запроса не
откатывает сессию. После перезапуска проверяются оба ответа и журнал без повторов.
Python нужен проверяющему сценарию, не движку. [Эталон базы](../testdata/compat/0.0.1/README.md)
не содержит пользовательских данных и остаётся неизменным.
Отчёты `smoke_*.json` публикуются с выпуском. Публикация разрешена только после
успеха всех проверок; одних кросссборок недостаточно.
После публикации отдельные задачи повторно скачивают архив и `SHA256SUMS`
на каждой ОС и заново выполняют сценарий. Полный релизный workflow считается
успешным только после этих запусков; отчёты доступны в `published-smoke-*`.

Для кандидата создайте запись `0.0.2-rc.N` в CHANGELOG и тег `v0.0.2-rc.N`.
После успешной приёмки подготовьте запись итоговой версии и тег `v0.0.2`.
Commit тега обязан входить в `main`; существующие выпуски не перезаписываются.
После публикации повторно скачайте архивы, сверьте общий `SHA256SUMS` и
запустите `python tool/smoke_release.py --archive ARCHIVE.zip --checksums SHA256SUMS --tag TAG --report report.json`
на соответствующей ОС. Итоговую проверку запишите в отчёт выпуска.

Текущий кандидат проверяется по [плану приёмки 0.0.2](ACCEPTANCE-0.0.2.md).
Отчёт имеет схему 2: по каждому умению записываются исходный и сохранённый DPS,
предпросмотры, хеши и точный повтор после восстановления; `upgrade` содержит
версию прежнего набора, нового набора и результат перезапуска.
