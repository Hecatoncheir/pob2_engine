# Обнаружение сервера и время жизни

Сервер владеет режимом жизни, арендами клиентов и счётчиком активных задач. Клиент, запустивший процесс, не имеет особого статуса: отключение первого приложения сохраняет работу остальных.

## Запуск по профилю

Сначала соберите CLI: `go build ./cmd/pob2-engine`. На Windows:

```powershell
.\pob2-engine.exe connect --profile main --start-server
```

Команда находит совместимый сервер профиля, а при его отсутствии запускает отдельный процесс в режиме `automatic`. После подключения выводится информация о сервере. Клиент удерживает аренду до закрытия stdin или Ctrl+C. Для второго клиента выполните в другом терминале:

```powershell
.\pob2-engine.exe connect --profile main
```

После закрытия первого клиента второй продолжает работу. После закрытия последнего сервер дожидается задач и задержки `--idle-timeout`, затем завершается. По умолчанию задержка составляет 5 секунд, срок аренды — 15 секунд. Повторное подключение в течение задержки сохраняет экземпляр и его сессии.

На Linux и macOS используйте `./pob2-engine`. Существующий сервер по-прежнему доступен через `--address` и `--token`. `--start-server` требует профиль; ошибка подключения без этого флага не запускает новый процесс. Создание сервера не создаёт сборку: сессия выбирается или создаётся отдельной командой.

```powershell
.\pob2-engine.exe session create --profile main --session build --name 'Общая сборка' --request-id create-1
.\pob2-engine.exe mcp --profile main --attach build
.\pob2-engine.exe info --profile main
```

Каждая команда CLI получает собственную краткую аренду. `connect` и MCP удерживают её всё время работы. `info` поэтому включает собственный клиент в счётчик; внутренние проверки обнаружения выполняются без регистрации и не продлевают жизнь сервера.

## Режимы и настройки

| Режим | Завершение |
| --- | --- |
| `automatic` | Нет живых клиентов и задач в течение `idle-timeout` |
| `persistent` | Явная команда `shutdown`, Ctrl+C или поддерживаемый сигнал ОС |

Обычный `serve` по умолчанию постоянный. Для публикации в профиле:

```powershell
.\pob2-engine.exe serve --profile main --mode persistent
.\pob2-engine.exe shutdown --profile main
```

Команды выполняются в разных терминалах. `connect --start-server` повторно использует такой сервер и сохраняет его постоянный режим. Параметры `--idle-timeout` и `--lease-timeout` у клиента применяются только при запуске нового automatic-сервера. Минимальные значения — 50ms и 100ms соответственно; максимальный срок аренды — 24h.

## Файл подключения и блокировки

По умолчанию файлы расположены в `<os.UserCacheDir()>/pob2-engine/<профиль>/`. Флаг `--runtime-dir DIR` меняет базовый каталог: итоговый путь — `DIR/pob2-engine/<профиль>/`. Имя профиля содержит до 64 букв ASCII, цифр, дефисов или подчёркиваний и начинается с буквы или цифры.

- `connection.json` содержит адрес loopback, токен, версию протокола, режим, PID и случайный `instance_id`.
- `server.lock` удерживается сервером до завершения задач, удаления собственного файла и остановки транспорта.
- `launch.lock` последовательно обслуживает конкурирующие запросы автозапуска.
- `server.log` содержит диагностику запущенного дочернего процесса.

Запись подключения публикуется атомарной заменой. Подключение проверяет токен, протокол и `instance_id` через настоящий RPC. PID не используется как доказательство работоспособности: устаревшая запись восстанавливается только при свободной блокировке экземпляра. Это работает и при повторном использовании порта посторонним сервером: он сохраняется, новый экземпляр получает другой порт. При занятой блокировке живой несовместимый сервер или несовпадение идентификатора возвращают ошибку. Занятая блокировка при отсутствующем ответе означает ожидание до таймаута, а не запуск второго экземпляра.

В Windows блокировка использует [LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex), в Linux/macOS — `flock`. Каталоги защищаются правами текущего пользователя: `0700`, файлы — `0600` на Unix; на Windows устанавливается DACL текущего пользователя с наследованием для файлов. Сам базовый каталог `--runtime-dir` не меняется. Файл подключения содержит секрет и не предназначен для публикации.

При остановке удаляется только запись со своим `instance_id`, пока удерживается `server.lock`. Файлы блокировок остаются: их нельзя удалять для принудительного снятия действующей блокировки. После аварийного завершения процесс теряет системную блокировку; следующий явный автозапуск заменяет устаревшую запись.

## Аренды клиентов

Дополнительные RPC описаны в [session.proto](../api/pob2/v1/session.proto):

1. `GetServerInfo` проверяет протокол и сообщает `instance_id`, режим, количество клиентов, задач и срок аренды.
2. `RegisterClient` принимает уникальный `client_id` приложения и `kind`: `ui`, `mcp` или `cli`. Возвращает `lease_id` и `lease_timeout_ms`.
3. `Heartbeat` продлевает аренду. Go-клиент вызывает его каждые `lease_timeout / 3` независимо от таймаута исходного подключения.
4. `ReleaseClient` освобождает аренду; повтор безопасен. Аварийное завершение очищается после истечения аренды.

Все RPC требуют `authorization: Bearer ТОКЕН`. Зарегистрированный клиент добавляет metadata `pob2-lease: LEASE_ID`. Истёкшая аренда отклоняется с `FailedPrecondition`. Повтор регистрации того же `client_id` и типа продлевает существующую аренду; другой тип для занятого идентификатора возвращает `AlreadyExists`. Лимит — 4096 клиентов на процесс.

Go-клиент автоматически регистрируется, подтверждает активность и освобождает аренду. При кратком сетевом сбое он повторяет heartbeat до истечения срока, затем закрывает соединение. Для повторного подключения нужен новый клиент; независимая сборка автоматически не создаётся. Старые вызовы без metadata аренды учитываются как задачи на время RPC, но не удерживают сервер между запросами. Будущему Flutter-клиенту нужно реализовать аренды; сам Flutter в этом этапе не изменялся.

## Задачи и остановка

RPC работы со сборкой автоматически учитываются как активные задачи. Для будущей фоновой работы сервис получает отдельную ссылку до постановки задачи в очередь:

```go
finish, err := manager.BeginTask("")
if err != nil {
    return err
}
go func() {
    defer finish()
    work(manager.Context())
}()
```

Пустой идентификатор здесь обозначает внутреннюю задачу. `finish` идемпотентен. Отключение клиента не отменяет фоновые задачи: выбранная политика — дождаться их завершения. Регистрация, начало задачи и решение об автоматической остановке проверяются под одним mutex.

При явной остановке сервер переходит в `draining`, запрещает новые регистрации и задачи и ждёт существующие RPC и фоновые задачи до пяти секунд. Затем принудительно закрывает транспорт и отменяет контекст задач. Ожидание не зависает на обработчике, игнорирующем отмену. Сохранения на диск пока нет: подтверждённые правки находятся в памяти до завершения процесса.

Клиент с `--start-server`, обнаружив завершающийся экземпляр, ждёт освобождения его блокировки и запускает новый. Существующие сессии при этом не восстанавливаются. Проверки с отдельными процессами покрывают одновременный запуск, уход первого и последнего клиента, аварийное отключение, удержание MCP, фоновую задачу, устаревший PID, постоянный режим и замену завершающегося экземпляра. CI выполняет тесты и проверку гонок только на Linux. Кросссборки трёх платформ запускаются только при выпуске по тегу.
