# Задержка получения сцены дерева

В Lua обработчик полной сцены возвращает команды штатной отрисовки PoB.
Ключи для выделения подсветки строятся при первом запросе подсказки со
сценой и переиспользуются для того же XML. Координаты, UV и цвет кодируются
как числовые массивы через `__tojson`. Векторы другой формы или числа в
локали с другим десятичным разделителем кодирует `dkjson`. Go обменивается
с Lua строками JSON, а клиенты получают сцену через gRPC.
[Кодирование векторов](../internal/pob/bridge/tree_scene.lua),
[подсветка](../internal/pob/bridge/worker.lua).

## Замер сцены

Windows x64, LuaJIT 2.1, PoB v0.23.1, `witch_fireball.xml` и назначение
Raw Destruction (51184). Оба бинарника использовали одну копию PoB с
фиксированным порядком обхода части таблиц отрисовки. На вариант пришлось
два первых и шесть прогретых замеров. Граница измерения — получение
ответа gRPC.

| Этап, медиана | До | После |
| --- | ---: | ---: |
| Первая полная сцена в новом процессе | 1001 мс | 722 мс |
| Полная сцена после назначения, прогретый процесс | 984 мс | 662 мс |
| Первая подсветка после этой сцены, прогретый процесс | 671 мс | 578 мс |
| Сцена и первая подсветка вместе, прогретый процесс | 1693 мс | 1418 мс |

Медианы рассчитаны как среднее двух центральных значений. Совместное
время посчитано по сумме двух вызовов в каждом прогоне. Максимум задержки
прогретой сцены составил 1079 мс до изменения и 1231 мс после.

Стенд сверяет состав и поля команд сцены и подсветки до и после назначения.
Хеши порядка команд сохраняются отдельно, поскольку порядок может
различаться между процессами Lua. Совпали также XML, ревизии, пять
добавленных пассивов и изменение `TotalDPS` с 12,817708 до 19,482917.
Сырые данные сохранены в
`.reference/tree-go-port-51184/geometry-ab.json` и `arm-*-rev-*-*.json`
из того же каталога.

## Штатный гибридный обход

Расчётный процесс включает гибридный поиск путей дерева на Windows, Linux
и macOS при совпадении SHA-256 `Classes/PassiveSpec.lua` с эталоном PoB
v0.23.1. Lua по-прежнему перестраивает зависимости и считает расстояние
от класса до гнёзд самоцветов. При пяти и более корнях Lua передаёт граф в Go
одним вызовом и восстанавливает пути. До пяти корней выполняется поиск Lua.
При другой ревизии `PassiveSpec.lua`, переопределённых методах и ошибке передачи
графа используется поиск PoB. Для контрольного прогона режим можно закрепить
переменной `POB2_ENGINE_TREE_PATHS=lua`.

Процессные тесты на сборке ведьмы сверяют расстояние, корень, порядок
узлов пути и расстояние до стартового класса. Отдельно тесты сравнивают
XML и полный отчёт после назначения и снятия 51184 в комплекте оружия I.

## Стоимость переноса поиска путей в Go

Прототип сверили с Lua на четырёх снимках активной спецификации по 4912
узлов. Снимки сделаны до и после назначения 51184 для общего режима и
второго комплекта оружия. Для каждого узла совпали расстояние, корень и
последовательность пути, включая различие между пустым и отсутствующим
путём. Данные и код опыта находятся в `.reference/tree-go-port-51184/`.

Медианы поиска в Lua составили 6,2–9,1 мс по пяти замерам на снимок.
Обход графа и построение путей в Go заняли 1,0–1,5 мс, а весь опыт
с разбором входного и кодированием выходного JSON в Go — 11,5–12,2 мс
по 60 замерам на снимок. Граница опыта — обработка JSON в памяти Go,
сверх неё интеграции потребовались бы передача данных и работа с ними
на стороне Lua. В этом опыте штатный поиск оставался в `PassiveSpec` PoB.

### Пакетный вызов Go из LuaJIT

В экспериментальной Windows-сборке `pob2_engine` LuaJIT вызывает алгоритм
Go один раз для всех корней. Граф, расстояния и связанные хвосты путей
передаются числовыми массивами. Lua восстанавливает обычные таблицы путей.
Обход расстояния от класса до гнезда самоцвета выполняется штатным Lua.
Эксперимент собирается через `go build -overlay` из файлов в
`.reference/go-path-ffi-20261125/`.

На PoB 0.23.1 проверены 911 пакетов обхода. Для каждого узла совпали
расстояние, корень и порядок пути. В матрицу вошли оба режима оружия,
обычные узлы, пустое гнездо и гнездо с самоцветом. В сравнениях через gRPC
совпали также полный отчёт, ревизия и SHA-256 XML.

| Полный цикл поиска путей | Lua | Go с передачей и восстановлением | Пакетов на вариант |
| --- | ---: | ---: | ---: |
| Первая версия моста | 6,23 мс | 7,35 мс | 104 |
| Мост с переиспользованием буферов | 5,04 мс | 4,27 мс | 104 |
| Один корень, переиспользуемые буферы | 4,52 мс | 4,30 мс | 80 |
| Шесть корней, переиспользуемые буферы | 7,92 мс | 3,99 мс | 20 |

В последней серии медиана вызова Go составила 0,37 мс, подготовка входа
заняла 1,75 мс, восстановление таблиц Lua — 1,83 мс. Сырые замеры и сводка
по числу корней сохранены в `.reference/go-path-ffi-20261125/profile-fast/`.

В двух чередующихся Release-сериях через gRPC использовался тот же
`witch_fireball.xml` и узел 51184. Для назначения и снятия было по 16
прогретых замеров на вариант, для первого отчёта — по восемь.

| Операция | Штатный Lua | Пакетный Go |
| --- | ---: | ---: |
| Назначение узла | 284 мс | 207 мс |
| Снятие узла | 237 мс | 193 мс |
| Назначение и первый отчёт | 348 мс | 264 мс |
| Первый отчёт в новом процессе | 1978 мс | 2189 мс |

Выигрыш назначения присутствовал в обеих сериях, а разница между
медианами составила 115 и 41 мс. Сводка хранится в
`.reference/go-path-ffi-20261125/release-summary.json`.

`pack_overlay.py` встраивает Lua-мост вместе с Go-обходом в экспериментальный
`pob2_engine_ffi_packed.exe`. Режим обхода Go включается через
`POB2_GO_PATH_MODE=go`. Для встроенного моста отдельно проверены сравнение
с Lua и рабочий обход Go. Сборка использует LuaJIT из установки PoB.

### Гибридный обход

Режим `POB2_GO_PATH_MODE=hybrid` использует Lua при числе корней до четырёх
и пакетный Go начиная с пяти. Для узла 51184 с одним корнем полный этап
поиска занял 4,66 → 4,53 мс, с шестью корнями — 9,57 → 4,08 мс.
Режим проверки сравнил и пути Go, и отложенный обход Lua с исходным PoB.

Холодный отчёт проверялся в 12 блоках из трёх свежих процессов одного
исполняемого файла. В каждом блоке два процесса использовали штатный Lua,
а один — гибрид. Порядок запуска менялся. Медиана парной разницы гибрида
относительно среднего двух Lua составила +27 мс, а медиана абсолютной
разницы между двумя Lua — 113 мс. В отдельном профиле холодного отчёта
по этой сборке все 12 пакетов гибрида выполнил Lua. Сырые данные сохранены
в `.reference/go-path-ffi-20261125/hybrid-cold/` и `hybrid-cold-profile/`.

| Назначение 51184 и получение отчёта | Lua | Гибрид | Замеров на вариант |
| --- | ---: | ---: | ---: |
| Ведьма Fireball, общий режим | 367 мс | 277 мс | 8 |
| Ведьма с ветвями оружия, комплект I | 386 мс | 267 мс | 6 |

При прямом сравнении постоянного Go и гибрида медиана парной разницы
назначения с отчётом составила +5 мс, снятия с отчётом — +9 мс. В каждом
режиме выполнено по восемь назначений и снятий. Сырые данные находятся в
`.reference/go-path-ffi-20261125/go-vs-hybrid/comparison.json`.

Сравнение выполнено в Windows Release с PoB 0.23.1. Полный отчёт, ревизия
и SHA-256 XML совпали. Проверка сокета с самоцветом прошла в обоих путях
гибрида. Сводка находится в
`.reference/go-path-ffi-20261125/hybrid-summary.json`, исполняемый файл —
в той же папке под именем `pob2_engine_ffi_hybrid.exe`.

## Профиль узла 51184 после v0.0.18

Повтор на Windows x64, LuaJIT 2.1 и PoB v0.23.1 с тем же
`witch_fireball.xml`. LuaJIT брал сэмпл каждые 4 мс. Таблица показывает
верхний Lua-кадр в интерпретаторе и JIT для 22 прогретых запросов каждого
типа.

| Операция | Файлы с наибольшим числом сэмплов |
| --- | --- |
| Отчёт | `PassiveSpec.lua` 440 из 814, `Common.lua` 118, `ModDB.lua` 43 |
| Применение пассива | `PassiveSpec.lua` 512 из 844, `Common.lua` 84, `PassiveTreeView.lua` 37 |
| Полная сцена | `dkjson.lua` 566 из 1751, `PassiveSpec.lua` 430, `tree_scene.lua` 271 |

Два отдельных вызова на операцию со счётчиком `debug.sethook` и
отключённым JIT дали в среднем 166 тыс. вызовов `Common.lua`, 64 тыс.
`PassiveTreeView.lua` и 51 тыс. `ModDB.lua` на отчёт. На полную сцену
пришлось около 1,86 млн вызовов `dkjson.lua`, на подсказку с подсветкой
около 883 тыс. Задержки измерены отдельно с включённым JIT.

Загрузка XML и построение спецификации заняли 229,4 из 238,1 мс
прогретого отчёта. Из 238,8 мс применения пассива 218,2 мс заняла
загрузка XML. При получении полной сцены кодирование JSON занимало
255,5 мс, запись ответа в канал 85,0 мс.

Внутренний ответ полной сцены теперь передаёт словарь строк и числовые
ряды команд. Go разворачивает ряды в `build.TreeScene` в исходном порядке.
Lua использует прежний формат для неподдерживаемой локали или формы
вектора. [Упаковка Lua](../internal/pob/bridge/tree_scene.lua),
[распаковка Go](../internal/pob/tree_scene_wire.go).
В повторном профиле кандидата по семи прогретым запросам упаковка
заняла 10,3 мс, кодирование JSON 98,2 мс, запись в канал 34,0 мс.

Последовательный A/B через gRPC использовал оба бинарника по очереди,
одну и ту же установку PoB и один XML. На вариант пришлись четыре первых
и двенадцать прогретых замеров. Подсветка между запросами в этом прогоне
отсутствовала.

| Этап, медиана прогретых запросов | До | После |
| --- | ---: | ---: |
| Начальная полная сцена | 820 мс | 534 мс |
| Полная сцена после назначения | 729 мс | 553 мс |
| От применения до получения отчёта | 694 мс | 729 мс |

В отдельном прогоне с запросом подсветки медиана полной сцены после
назначения составила 797 и 775 мс. Состав и поля команд обеих сцен и
подсветки совпали. XML, ревизии, пять назначенных узлов и изменение DPS
с 12,817708 до 19,482917 совпали в обоих прогонах. Граница замера
заканчивается ответом gRPC.

Сырые результаты находятся в
`.reference/lua-profile-next-51184/summary.json`,
`.reference/lua-profile-next-51184/packed-edit-ab.json`,

в `.reference/lua-profile-packed-51184/summary.json`. Замер без подсветки

## Повторный отчёт сборки

Движок хранит один готовый отчёт Lua. Ключ включает XML, переданный PoB,
и имя сборки. Сервис проверяет ожидаемую ревизию перед чтением, а при
остановке процесса Lua сохранённый отчёт очищается.

Release-замер на Windows с PoB 0.23.1 выполнен через gRPC на
`witch_fireball.xml`. На каждый вариант пришлось четыре новых процесса.
Порядок запуска базовой сборки и кандидата чередовался.

| Запрос отчёта | Медиана до | Медиана после | Замеров на вариант |
| --- | ---: | ---: | ---: |
| Первый в новом процессе | 2119 мс | 2157 мс | 4 |
| Повтор для того же XML | 217 мс | 1 мс | 16 |
| Первый после назначения узла 51184 | 266 мс | 226 мс | 8 |
| Повтор после назначения | 238 мс | 1 мс | 16 |
| После расчёта с новой ревизией и тем же XML | 238 мс | 1 мс | 8 |

Первый запрос после назначения читает изменившийся XML и заново строит
отчёт. Разницу между сериями этого запроса учитываем как разброс замера.
В обеих сборках совпали полные отчёты и SHA-256 XML. После назначения
`TotalDPS` вырос с 12,817708 до 19,482917, устаревшие ревизии отклонены.
Сырые результаты сохранены в `.reference/report-reuse-20261125/comparison.json`.

## Первый отчёт после правки

При установке экипировки проверка слота уже загружает итоговый XML.
Следующий запрос отчёта может использовать рассчитанную сборку. При правке
пассивов движок сверяет XML с подтверждённым Lua изменением и обновляет
показатели штатным кадром PoB. Любая промежуточная команда расчётчика
сбрасывает подготовленное состояние. Для сборок с автоуровнем отчёт после
правки пассива строится из XML, поскольку следующий кадр может взять
другой уровень персонажа.

Замеры gRPC выполнены на Windows в Release с PoB 0.23.1. Для пассива
использованы `witch_fireball.xml` и узел 51184, для экипировки — нагрудник
Release Ward в `testdata/reference/0.0.5/attacker.xml`.

| Первый отчёт после правки | Медиана до | Медиана после | Замеров на вариант |
| --- | ---: | ---: | ---: |
| Установка нагрудника | 202 мс | 8 мс | 8 |
| Назначение узла | 224 мс | 61 мс | 6 |
| Снятие узла | 231 мс | 56 мс | 6 |

По сумме времени `Apply` и чтения отчёта назначение ускорилось с 449 до
330 мс, а снятие — с 483 до 288 мс. Полные отчёты и SHA-256
XML совпали. Проверка автоуровня отдельно сравнила полный отчёт с
обычной загрузкой XML. Сырые результаты сохранены в
`.reference/first-gear-report-20261125/comparison.json` и
`.reference/first-passive-report-20261125/final-ab/comparison.json`.

## Проверка

Локальный стенд замера gRPC из `.reference/tree-go-port-51184/time-geometry/`
принимает два бинарника и один каталог PoB для обоих через `--baseline-pob`
и `--candidate-pob`. Для этого опыта используются `--fixture` с путём к
`witch_fireball.xml`, `--node 51184 --cold 2 --warm 6`.

Процессный тест сначала получает полную сцену, затем сверяет подсветку,
подсказку и путь через CLI, MCP и gRPC. Из корня репозитория задайте
`POB2_ENGINE_POB_DIR` с путём к установке PoB и выполните команду.

```powershell
go test ./internal/integration -run 'TestLuaTree(Geometry|NodeTooltip)AcrossProcesses' -count=1
```
