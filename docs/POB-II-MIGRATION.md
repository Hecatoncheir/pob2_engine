# Переход основной мастерской PoB II на pob2_engine

## Цель

В стабильном PoB II 1.x основная мастерская открывает и редактирует
сборку в сессии `pob2_engine`. Go принимает команды CLI, MCP и gRPC,
проверяет ревизии и сохраняет результат. Оригинальный Lua PoB рассчитывает
сборку и проверяет игровые ограничения. Flutter показывает редактор,
рисует дерево и управляет окнами.

Базой для переноса служат функции редактора ветки `1.x.x` на коммите
`5b3f2119e52aa9761ac3d29302cebf4904527002` и движок v0.0.11.
[Сценарии PoB II](https://github.com/Hecatoncheir/pob2_ui/blob/5b3f2119e52aa9761ac3d29302cebf4904527002/README.md#что-работает) ·
[Приёмка движка](../testdata/releases/0.0.11/README.md).

## Этапы

| Этап | Что переносим | Проверяемый результат |
| --- | --- | --- |
| 1. Ветви оружия | Режимы назначения, снятие, предпросмотр и очки для обоих комплектов. [План 0.0.12](../todo_0.0.12.md) | CLI, MCP, gRPC и общая сборка PoB II показывают путь оригинального Lua. |
| 2. Одна сборка в мастерской | Открытие XML в сессии, стабильная привязка к записи библиотеки, просмотр расчёта и первая правка условия. | Правка в штатном редакторе видна через MCP, сохраняется в XML и восстанавливается после перезапуска. |
| 3. Дерево | Геометрия и ресурсы, подсказки, сравнение путей, поиск влияния, мастерства, гнёзда, восхождения и спецификации. | Существующие сценарии дерева проходят на том же XML с совпадением режимов, очков и результатов Lua. |
| 4. Умения, экипировка и условия | Полные формы групп и поддержек, выбор умения и его части, редактор предметов, оружие и зависимые слоты, каталог условий, подробный отчёт. | Предпросмотр, применение и отчёты совпадают для контрольных сборок, включая предупреждения о камнях и предметах. |
| 5. История и библиотека | Undo/Redo через ревизии, применение этапа прокачки одной командой, заметки, копии, коды PoB, ссылки, импорт из оригинального PoB и файловые конфликты. | Старые XML, резервные копии и заметки переживают обновление, правку через MCP, конфликты и восстановление. |
| 6. Инструменты MCP и поставка | Совместимость нужных инструментов редактора, запуск и обновление движка из установщика, проверка профиля и откат. | Установленный PoB II управляет общей сборкой через gRPC, а команды MCP для окон и диалогов работают через приложение. |
| 7. Релиз PoB II 1.x | Кандидат, приёмка на Windows x64, Linux x64 и macOS arm64, стабильный выпуск и проверка скачанных установщиков. | Все сценарии этапов приняты в штатном редакторе на чистом профиле и после обновления предыдущего выпуска. |

## Как принимать перенос

- Для каждого сценария закрепить исходный XML, действие, версию Lua,
  ожидаемые поля, диагностику, изменение файлов и поведение при ошибке.
  Использовать сценарии существующего редактора как эталон.
- Проверять операции сборки через CLI, MCP и gRPC до подключения Flutter.
  Операцию с предпросмотром сверять по состоянию, расчёту и хешу XML.
  Успешная запись даёт одну ревизию и одно событие.
- Проверять запрет применения устаревшего предпросмотра, повтор запроса,
  переподключение, отмену и сохранность XML при внешней правке. Библиотека
  сохраняет переносимые XML, журнал движка восстанавливает сессии и ревизии.
- По мере переноса запускать действующие тесты PoB II с новым сервером.
  Перед релизом принять расчёт, дерево, редакторы, библиотеку, автоматизацию
  MCP, установку, обновление и откат на трёх нативных раннерах.

Промежуточные версии движка можно выпускать после приёмки соответствующего
этапа. Публикация PoB II 1.x опирается на полный набор проверок штатной
мастерской, включая импорт из оригинального PoB через внешний адаптер.

## Открытие сборки и первая сквозная правка

1. Создать общую сессию из XML открытой сборки одним вызовом. Импорт
   использует тот же XML, что и экспорт из мастерской, с заметками и этапами.
   Проверить первую ревизию и повторное чтение XML через gRPC. Этот шаг
   реализован в локальном коммите PoB II `63e8e5d` и проверен
   процессным тестом.
2. Связать запись библиотеки с явным идентификатором сессии и отслеживать
   последнюю применённую ревизию входных данных. При открытии сначала
   принимать состояние сессии, затем подписываться на последующие изменения.
3. Отправить правку условия из существующей формы редактора как типизированный
   `ConfigEdit` с ожидаемой ревизией. После подтверждения принять XML из
   снимка и сохранить через существующую проверку версии файла.
4. Сверить XML, условие и расчёт из мастерской, CLI и MCP. Во время правки
   внести внешнее изменение, проверить конфликт, повторное открытие и принятие
   актуального снимка. При расхождении с файлом показать доступные версии
   средствами библиотеки.
