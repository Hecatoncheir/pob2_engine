# Задержки назначения пассива через gRPC

Из корня репозитория запустите команду с двумя собранными бинарниками
и двумя подготовленными каталогами PoB одной версии.

```powershell
go run ./tool/measure_tree_latency --baseline .reference/source.exe --candidate .reference/candidate.exe --baseline-pob .reference/pob-source --candidate-pob .reference/pob-candidate --cold 3 --warm 20
```

По умолчанию используется [эталон Воина](../../testdata/reference/0.0.10/warrior.xml)
и узел 13397. Для другой сборки задайте `--fixture` и `--node`
с идентификатором доступного неназначенного пассива. Опции
`--workbench=false` и `--geometry=false` исключают отдельные этапы.

Холодный замер начинается в новом процессе с отдельным временным профилем.
Прогретые замеры открывают одну и ту же исходную сборку в новых сессиях
того же процесса. Порядок запуска двух бинарников меняется каждый раунд.
Кэш файлов операционной системы сохраняется между запусками.

Замеры открытия охватывают создание сессии из XML, загрузку XML в рабочую
копию, отчёт Lua и полную сцену дерева. Замеры назначения охватывают
предпросмотр, подтверждение и обновление тех же данных. Итоговые интервалы
складывают времена соответствующих вызовов. Время запуска процессов,
отрисовка Flutter, загрузка текстур и сохранение в библиотеку PoB II
лежат за пределами этих интервалов.

Программа проверяет чистоту предпросмотра, последовательность ревизий,
путь к узлу, хеши XML и числовые показатели. Оба бинарника должны вернуть
одинаковый результат. JSON в stdout содержит сырые значения, p50 и p95
в наносекундах. Журнал дочерних процессов идёт в stderr.
