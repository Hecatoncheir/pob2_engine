# Быстрое открытие PoB II и работа с деревом

## Порядок работ

1. [x] Открывать последнюю XML-сборку сразу в общей сессии. Сохранить проверки ревизии, внешних правок XML и запуск локальной мастерской при недоступности общей сессии.
2. [x] Загружать полную геометрию и текстуры при открытии вкладки дерева. Для редакторов, которым нужна геометрия, выполнять запрос по действию пользователя.
3. [x] Переиспользовать отдельный Lua-процесс для предпросмотра черновика группы. На каждом запросе заново загружать текущий XML. После ошибки сбрасывать процесс, при закрытии мастерской завершать его.
4. [x] Сохранять последнюю полную сцену дерева между запусками. Повреждённый кэш восстанавливать из Lua.
5. [x] Сравнить замеры до и после на Windows. Проверить XML, расчёт Lua и восстановление после перезапуска.
6. [x] Показывать интерактивные узлы и связи сразу после получения геометрии. Текстуры догружать поверх дерева, начиная с видимой области.
7. [x] Запрашивать недостающие текстуры пакетами по атласам. Сравнить время до интерактивного дерева и до полного оформления на одинаковом XML и PoB.
8. [x] Отложить запуск рабочей копии Lua до первой операции, которой она нужна. Проверить первый вход в редактор группы и прогрев Lua для предпросмотра без задержки открытия сборки.
9. [ ] При выпуске принять кандидат на Windows, Linux и macOS и закрепить бинарник движка в сборке PoB II.

## Кэш дерева

Сервер хранит геометрию и команды отрисовки Lua в `last-tree-scene.gz`
рядом с журналом сессий профиля. Для тестовой сборки запись занимает
около 0,94 МиБ. Кэш хранит одну сцену и учитывает полный расчётный XML,
версию движка, формат кэша и контрольную сумму архива PoB. XML включает
класс, восхождение, пассивы, комплекты оружия и самоцветы. По запросу с
другим ключом сервер строит новую сцену. Кэш включён для управляемых
установок PoB и постоянных профилей сервера. Flutter использует прежний
дисковый кэш текстур и рисует сцену при текущем масштабе.

Повторная генерация в оригинальном Lua может менять порядок некоторых
команд и ссылки на атласы. На проверенной сборке совпали координаты,
узлы, связи и набор геометрических команд. Кэш воспроизводит исходный
кадр целиком. После повреждения файла сервер заново получает сцену из Lua.

## Замеры на Windows

Исходные версии — PoB II 1.0.3 и pob2_engine 0.0.16. В обеих версиях
использовался установленный PoB 0.23.1. Сценарий приложения запускал
сборку Windows Release в изолированном профиле с XML
`integration_test/fixtures/witch_fireball.xml`. Первые три запуска
восстанавливали сборку. Следующие четыре запрашивали дерево и ждали
готовности текстур. Приложение перезапускалось на каждом прогоне при
штатном жизненном цикле сервера. Сценарий с остановленным сервером
проверялся ещё тремя попеременными запусками каждой версии.

| Измерение | До | После |
| --- | ---: | ---: |
| От запуска PoB II до первого отчёта Lua | 3,58 с | 0,66 с |
| От запуска PoB II до готовности общей сессии | 8,60 с | 2,68 с |
| От запуска PoB II до первого отчёта Lua с остановленным сервером | 4,04 с | 2,52 с |
| От запуска PoB II до готовности общей сессии с остановленным сервером | 8,71 с | 2,58 с |
| От запуска PoB II до дерева при первом запросе оформления в серии, один прогон | 17,69 с | 16,71 с |
| От запуска PoB II до дерева при заполненном кэше текстур | 11,02 с | 4,14 с |
| Полная сцена по gRPC, первый запрос | 1,11 с | 1,19 с |
| Полная сцена по gRPC после перезапуска сервера | 1,11 с | 0,11 с |
| Предпросмотр поддержки через MCP, первый запрос | 2,38 с | 2,43 с |

В таблице указаны медианы трёх прогонов, кроме первого открытия с
ожиданием оформления и девяти повторных предпросмотров. Замеры gRPC и MCP
использовали `testdata/reference/fireball.xml`. На каждом прогоне gRPC
сервер получал отчёт Lua перед замером запроса сцены. Повторный запрос
делался после остановки и запуска сервера с тем же профилем. Проверены
точное совпадение сцены из кэша и восстановление после повреждения
файла. После повторных предпросмотров совпали результат, XML и ревизия.

При восстановлении приложения совпали XML, заметки, состояние общей
сессии и расчёт Lua. Отдельная регрессия подтвердила, что отложенное
дерево приходит по запросу, правка XML с диска попадает в общую сессию,
а независимая правка с двух сторон сохраняет обе версии. На Windows
также прошли процессные проверки CLI, MCP и gRPC с исходным Lua,
`go vet ./...`, `go test ./...`, анализ Dart и 36 модульных и
виджетных тестов PoB II.

## Догрузка оформления и запуск рабочей копии

Flutter показывает узлы и связи после запроса геометрии. Оформление
догружается в фоне, начиная с видимой области. При подстановке сцены
сохраняются центр, масштаб и выбранный узел. Сервер читает один атлас
на пакет и декодирует до трёх слоёв одновременно, сохраняя порядок ответов.

Мастерская gRPC принимает соединение сразу. Рабочий Lua запускается
при первом запросе, для которого нужен расчёт. При открытии редактора
существующей группы поиск поддержек запускается сразу после загрузки
каталога. Восстановление сборки не запрашивает каталог классов.

Замеры сделаны на Windows Release с PoB 0.23.1. Сравнивались две
локальные сборки 0.0.17. В изолированном профиле использовались
один XML и одна сохранённая общая сессия. Перед каждым прогоном
штатно останавливался сервер и освобождались кэши сцены и текстур.
В таблице указаны медианы трёх запусков каждого варианта.

| Измерение | До | После |
| --- | ---: | ---: |
| Готовность общей сессии от запуска приложения | 2,56 с | 2,57 с |
| Первый кадр дерева с геометрией от запроса | 1,38 с | 0,49 с |
| Все текстуры доступны приложению от запроса | 11,18 с | 6,57 с |

В отдельной серии из трёх запусков мастерская начинала принимать
соединение gRPC за 2,10 с до изменений и за 0,07 с после. Запуск Lua
в обновлённой мастерской входит во время первой операции с расчётом.

Во всех прогонах совпали XML, сохранённая сессия и результат расчёта
Lua. CI на трёх платформах входит в приёмку кандидата.
